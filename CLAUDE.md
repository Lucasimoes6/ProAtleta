# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

- **Backend:** Java 17 + Spring Boot 3.3 + Spring Security + JPA/Hibernate + JJWT 0.12
- **Frontend:** React 18 + TypeScript + Vite + Zustand + React Router 6 + Axios + Recharts
- **DB:** H2 in-memory for `dev` profile, PostgreSQL for `prod` profile

Monorepo with `backend/` (Maven) and `frontend/` (npm) as siblings.

## Common commands

```bash
# Backend (from ./backend)
mvn spring-boot:run                    # dev server on :8080 with H2
mvn test                               # run all tests
mvn test -Dtest=ClassName#method       # single test
mvn clean package                      # produces target/*.jar

# Frontend (from ./frontend)
npm install
npm run dev                            # Vite on :5173, proxies /api to :8080
npm run build                          # tsc -b && vite build
npm run lint                           # tsc --noEmit (type check only)
```

H2 console at `http://localhost:8080/h2-console` — JDBC URL `jdbc:h2:mem:athlete`, user `sa`, no password.

To run against PostgreSQL set `SPRING_PROFILES_ACTIVE=prod` plus `DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD`, and `JWT_SECRET` (must be ≥32 bytes — `JwtService` throws on shorter).

## Architecture

### Vertical slicing by feature

The backend is organized by **feature package**, not by layer. Each feature owns its entity, repository, controller, DTOs, and any domain services in one folder:

```
com.health.athlete.{auth,athlete,anamnesis,training,injury}
```

Cross-cutting concerns live in `config/` (Spring Security + CORS) and `common/` (global exception handler, shared exceptions). When adding a new feature, follow the same vertical-slice pattern rather than introducing horizontal layers.

### Domain pipeline

The user-facing flow drives a chain of dependent entities — understand this before touching any single feature:

1. **`User`** authenticates → JWT issued by `JwtService`, validated per request by `JwtAuthenticationFilter`. `User` itself implements `UserDetails`, so controllers receive it via `@AuthenticationPrincipal User`.
2. **`Athlete`** is a 1:1 extension of `User` keyed on `user_id`. Created/updated via `PUT /api/athletes/me`. Without an `Athlete` row the anamnesis and training endpoints return 404.
3. **`Anamnesis`** belongs to an `Athlete` and is the input to all intelligence. On create, `AnamnesisEvaluator` runs heuristic rules to produce `autoReport` (BMI, alerts on HR/sleep/stress, sport-specific valency focus). The persisted entity is the latest snapshot — history is immutable.
4. **`TrainingPlan`** is generated by `PeriodizationEngine.generate(athlete, latestAnamnesis, startDate)` from the latest anamnesis. The engine produces a 12-week plan with 4 phases (BASE → INTENSIDADE → PICO → RECUPERACAO), modulating `volumeLoad` and `intensityLoad` per phase × conditioning level. Sessions are picked from sport-specific templates and split across the week based on `trainingDaysPerWeek`.
5. **`Injury`** triggers `RehabProtocols.generate(region, severity)` to build a phased rehab text on creation. Injuries do not currently auto-modify the active `TrainingPlan` — that integration is a known extension point.

### Why this matters when extending

- Replacing the heuristic intelligence: both `AnamnesisEvaluator` and `PeriodizationEngine` are `@Component`s with no external state. Swap them with LLM-backed implementations by introducing an interface in front and adding a new bean — controllers don't need to change.
- Wearables: there is no integration yet. Plan is to add `POST /api/wearables/sync` and feed metrics into `Anamnesis` (or a new entity) so the engine picks them up on next plan regeneration.
- Coach role: the `User.Role.COACH` enum value exists but no UI/endpoint enforces coach-athlete relationships. Adding a `coach_id` FK on `Athlete` is the expected path.

### Persistence note

`spring.jpa.hibernate.ddl-auto=update` is enabled in both profiles. There is no migration tool yet — adopt Flyway/Liquibase before a real deployment, otherwise schema drift will silently corrupt prod.

### Frontend state model

- **Auth state** lives in Zustand (`src/store/auth.ts`) with `persist` middleware → token survives reloads in `localStorage` under key `athlete-auth`.
- **Server state** is fetched ad-hoc inside pages via `useEffect` + the typed clients in `src/api/endpoints.ts`. There is no React Query or SWR layer — keep this in mind before adding caching.
- **Axios interceptors** (`src/api/client.ts`) inject the bearer token on every request and force `logout()` on any 401 response.
- **Routing** in `App.tsx` gates the entire app on token presence: unauthenticated users only see `/login` and `/register`; authenticated users get the `Layout` shell with sidebar nav.
- Path alias `@/*` → `src/*` is configured in both `tsconfig.json` and `vite.config.ts` — keep them in sync.

### Security configuration

`SecurityConfig` is stateless (no sessions). Public routes are explicitly listed: `/api/auth/**`, `/h2-console/**`, `/actuator/health`, plus all `OPTIONS` for CORS preflight. Everything else requires a valid JWT. CORS allows `http://localhost:5173` and `http://localhost:3000` by default — extend the list there if deploying the frontend elsewhere.
